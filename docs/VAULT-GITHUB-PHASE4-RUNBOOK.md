# Vault Phase 4 cutover and restore

Status: code path prepared; production cutover has **not** been performed. The Phase 3 verification report was absent from this checkout on 2026-09-25. Do not claim an empty legacy Vault without a timestamped, project-by-project production inventory.

## Authority and prerequisites

Set `VAULT_CUTOVER_AUTHORITY` to a high-entropy operator secret on the backend and `VAULT_DRIVE_RETENTION_DAYS` to the owner-approved retention period. An authenticated ClubPM admin must also send the authority in `X-Vault-Cutover-Authority`. Keep the header out of logs. Apply the Phase 1 and Phase 4 Prisma migrations before using these routes. Keep the job directory durable. Confirm App installation, branch rules, private repository, LFS cap, and Phase 0 large-file proof. No endpoint deletes Drive data or changes GitHub repository settings.

For each project, save `GET /api/projects/:id/vault/cutover` before and after every action. The response includes the state, legacy object counts (including soft-deleted items), pending upload count, head, error, and retention date. Use `GET /api/projects/:id/vault/repository/health` to inspect permissions and remote head. The API keeps each project's state independently.

## Sequence, one project at a time

1. Save the Phase 3 report, its inventory time, byte-length and SHA-256 verification ledger, CR/BOM link check, and owner acceptance outside this repository. Confirm it covers the project and every soft-deleted item. If any Drive-backed version, thumbnail, or unexplained Drive item folder remains, stop and finish Phase 3.
2. `POST /api/projects/:id/vault/cutover` with `{ "action": "freeze" }`. Both legacy and GitHub new writes pause. Drain and retry upload jobs; `GET /api/vault/upload-jobs/:jobId` shows each result. Do not activate while any job is `UPLOADED`, `LFS_STORED`, `COMMITTED`, or `RETRY`.
3. `POST` to the same endpoint with `{ "action": "record-phase3", "checkedAt": "<report UTC timestamp>", "counts": { "driveVersions": 0, "driveThumbnails": 0, "driveItems": 0 } }`. The server rechecks live counts. This step records the operator's report claim; keep the actual signed verification evidence separately.
4. `POST` with `{ "action": "activate" }`. The server rechecks counts and jobs, compares the remote branch head to the database, fetches and checks every pinned GitHub source and thumbnail against SHA-256 and byte length, rechecks the head, then enables GitHub writes. A failed step leaves the project frozen. Retention begins at the successful activation timestamp.
5. Monitor `GET /api/projects/:id/vault/cutover`, repository health, job errors, download errors, and the repository owner's LFS usage/cap. Signed webhooks reconcile pushes and installation changes. A five-minute poll covers missed webhooks. An external push sets `BRANCH_DRIFT`; inspect the Git diff and reconcile content before changing the expected head. Never automatically adopt an external commit into Prisma.

`AUTH` means restore App installation access. `PERMISSION` means repair the branch rule or App bypass. `GIT_ERROR` means retry after GitHub/transport recovery. `LFS_QUOTA` means raise the owner cap. `LFS_MISSING` means restore the missing pinned object from retained bytes. `BRANCH_DRIFT` means review an external push. Each error leaves activation blocked.

## Retry and rollback

After repairing a failed activation, keep the project frozen and call `activate` again; byte verification and remote-head comparison run again. For a failed upload job, use its existing retry endpoint and idempotency key. For an external push, freeze the project, review the commit and changed paths, then call `{ "action": "accept-reviewed-head", "reviewedHeadSha": "<40-character SHA>" }`. This refuses pending jobs and re-verifies pinned bytes before advancing the checkpoint. It does not import external metadata or new files into Prisma. Then retry activation. If the external push changed Vault metadata or files, resolve that drift by a separately reviewed repair before accepting the head.

To restore **new writes** to Drive while originals and Drive credentials remain available, call the cutover endpoint with `{ "action": "rollback" }`. GitHub-backed versions and thumbnails keep their provider-pinned reads. If the legacy Drive folder was never provisioned for a GitHub-created item, Drive check-in on that item cannot resume; use a fresh Drive-backed item or repair its folder under the existing provisioning flow. If the GitHub service is down, cached/private GitHub bytes are not promised; restore pinned Git/LFS objects from the verified backup before declaring reads healthy. Keep the source ledger and repository archive until the owner signs off.

After `retentionUntil`, a human must verify all projects have zero legacy objects, obtain owner acceptance, export/archive original Drive data and the Git repository, and test restoring a sample file by hash. Only then may a separate change remove Vault-specific Drive provisioning, upload, download, thumbnail, and setup code. Do not remove Files → Drive or unrelated Google integrations. This release deliberately retains those Vault paths because no Phase 3 verification report or elapsed retention window is available.

To restore a pinned GitHub object, use the report's `owner/repo`, branch, commit SHA, path, SHA-256, and byte length. In a private recovery workspace, clone with an authorized installation credential, check out the recorded commit, run `git lfs pull --include="<path>"`, and compare the downloaded file's SHA-256 and byte length to the ledger. If the LFS object is absent, recover the Drive original identified by the ledger, hash it, then re-upload the exact bytes to LFS in a controlled repair commit. Keep the old commit and version row pinned until the original object is actually readable again; never repoint the row merely to hide a failed read. Record the repair commit and verification result in the incident log. An archived Git bundle alone does not contain LFS payloads, so export LFS objects with the repository archive.
