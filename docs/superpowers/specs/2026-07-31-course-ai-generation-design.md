# AI Course Generation — Design

Third of three specs in the course-system upgrade. Depends on **modules**
(`2026-07-31-course-modules-design.md`) for the tree it emits and on **slides**
(`2026-07-31-course-slides-design.md`) for the `SLIDES` kind it can name.

## Context

`blogAiService` / `aiOutreachService` turn a prompt into one designed document via a validated
`SectionPlan`. That pattern works and is the right one to scale up: the model never emits raw TipTap
JSON, it emits a high-level plan that a deterministic builder maps into schema-valid nodes.

A course is that idea one level up — a plan of **modules and sections**, where each section then gets
its own body generated by the machinery that already exists. The difference that drives every
decision below is **duration**: a twelve-section course is thirteen-plus model calls and takes
minutes, so it cannot be an HTTP request.

## Decisions

| Decision | Choice |
|---|---|
| Execution | A `CourseGenJob` row + in-process async work; the client **polls**. Not SSE, not synchronous. |
| Author control | **Two stages.** A fast outline call → the author edits the outline → body generation runs against exactly that. |
| Emitted kinds | CONTENT (full bodies), QUIZ (real questions), SLIDES (outline prose only), VIDEO (titled placeholder). |
| Inputs | Long prompt + optional pasted reference material + optional published blog posts as source. |
| Plan validation | `coursePlan.ts`, modelled on `sectionPlan.ts`: coerce arbitrary model JSON into a clamped, known-shape plan. |
| Output | A **DRAFT** course the author then edits normally. Never published, never auto-assigned. |

## Non-goals

- Generating slide images, video, or audio. SLIDES gets an outline; VIDEO gets a title and a brief.
- Editing an existing course. This creates new courses only; per-section AI editing already exists.
- Publishing, assigning, or notifying anyone. A generated course is a draft until a human says so.
- A queue or worker process. Jobs run in the API process, and a restart fails them (see below).
- Regenerating one section from the review screen. Approve the outline or edit it by hand.

## The two stages

### Stage 1 — outline (seconds, one call)

`generateCourseOutline({ prompt, reference, sourcePosts })` → one `generateJsonComplex` call →
`validateCoursePlan` → stored on the job as `outline`, status `AWAITING_REVIEW`.

```ts
export interface PlanCourseSection {
  kind: "CONTENT" | "VIDEO" | "QUIZ" | "SLIDES";
  title: string;
  isRequired?: boolean;
  /** What this section must cover. The ONLY thing stage 2 sees per section. */
  brief: string;
  questionCount?: number;   // QUIZ
  passThreshold?: number;   // QUIZ
  slideCount?: number;      // SLIDES
}

export interface PlanCourseModule {
  title: string;
  summary?: string;
  estimatedMinutes?: number;
  isRequired?: boolean;
  sequential?: boolean;
  sections: PlanCourseSection[];
}

export interface CoursePlan {
  title: string;
  summary?: string;
  modules: PlanCourseModule[];
}
```

`validateCoursePlan` drops unknown kinds, clamps strings, and enforces **≤ 8 modules, ≤ 10 sections
per module, ≤ 50 sections total**. Those caps are the cost ceiling: the outline is the only thing
standing between a careless prompt and forty model calls.

### Stage 2 — bodies (minutes, one call per section)

Runs only after the author approves. In order:

1. Create the `Course` (DRAFT) and its `CourseModule` rows through `courseService`, so ordering,
   defaults, and the born-with-a-module rule are the same code paths the editor uses.
2. For each section, in outline order:
   - **CONTENT** → a `SectionPlan` call reusing `BLOG_PLAN_SCHEMA` from `aiOutreachService.ts`, then
     `buildDocFromPlan` → `contentJson`. Nothing new is invented here; it is the blog generator
     pointed at a section brief.
   - **QUIZ** → `generateQuizQuestions(brief, context)` → validated question rows written through
     `courseService.replaceQuestions(sectionId, questions, "quiz")`, so ids and response rows behave
     exactly as hand-authored questions do.
   - **SLIDES** → a slide outline (title + speaker notes per slide) rendered as **prose** into
     `contentJson`. No `CourseSlide` rows: there is no deck, and fabricating empty slides would leave
     the workbench in a state no import can cleanly replace.
   - **VIDEO** → title plus the brief as prose notes. `videoConfig` stays null.
3. After each section, update `progress` (0–100) and `stepLabel` ("Writing 4 of 11 — Engine cycles").
4. Set `status: DONE` and `courseId`.

**Each section's call sees the course title, its module title, its own brief, and the reference
material — not the other sections' generated bodies.** Feeding every prior body forward would grow
the prompt without bound and blow the token budget around section six. The outline is what makes the
sections cohere; that is its job.

### Quiz questions are grounded, not invented

A QUIZ section's call receives the **generated text of the CONTENT sections in its own module**,
extracted with `docToPlainText`. A quiz that tests material the course did not teach is the obvious
failure mode, and module-scoping is what keeps that prompt bounded. This is the one place stage 2
looks sideways at earlier output, and it is deliberately limited to one module.

## Job model

```prisma
enum CourseGenStatus {
  OUTLINING
  AWAITING_REVIEW
  GENERATING
  DONE
  FAILED
}

model CourseGenJob {
  id            String          @id @default(cuid())
  createdById   String
  createdBy     Member          @relation("CourseGenJobCreator", fields: [createdById], references: [id], onDelete: Cascade)
  status        CourseGenStatus @default(OUTLINING)
  prompt        String
  reference     String?
  sourcePostIds String[]        @default([])
  outline       Json?
  courseId      String?
  progress      Int             @default(0)
  stepLabel     String?
  error         String?
  createdAt     DateTime        @default(now())
  updatedAt     DateTime        @updatedAt

  @@index([createdById, createdAt])
}
```

**Polling, not SSE.** The author watches one screen for about two minutes. Polling `GET /:jobId`
every 2 s is a few dozen cheap reads, and it works identically after a refresh, on a second tab, and
on a reconnect — none of which SSE gets for free. The existing SSE channel is for ambient
notifications, not for a foreground progress bar.

**Jobs run in the API process** (`void runCourseGeneration(jobId)` after the response is sent). A
restart therefore abandons anything in flight. Rather than pretend otherwise, `app.ts` startup sweeps
any `OUTLINING` / `GENERATING` job older than 15 minutes to `FAILED` with
`"Interrupted by a server restart — start a new generation"`. A stuck-forever spinner is a worse
failure than an honest one.

**Cancel** sets `FAILED` with an author-cancelled message; the loop checks status between sections
and stops. Sections already written stay — the course exists as a partial draft, which is more useful
than deleting the author's half-generated work.

## Model budget

`generateJsonComplex` uses the complex model, capped at **25 requests/day**, and
`geminiService.ts:42-53` already falls back to the standard model when that is exhausted rather than
failing. One course is `1 + sectionCount` calls, so the second course of a day will run partly or
wholly on the standard model.

Two rules follow:

- **Fallback is not failure.** The job continues on the standard model. Quality drops; the job does
  not stop, and nothing surfaces an error for it.
- **A hard per-job ceiling of 60 model calls**, checked in the loop. The outline caps sections at 50,
  so this can only trigger on retries — which is exactly when a runaway is possible.

Calls are sequential. The rate limiter is a sliding window; firing eleven section calls in parallel
would trip it and convert a slow job into a failed one.

## Frontend

`CourseGenModal.jsx`, opened from `CoursesTab`'s "New course" menu as "Generate with AI":

1. **Brief** — a large prompt textarea (audience, goals, length, tone), an optional reference-material
   textarea, and a multi-select of published blog posts. → "Draft the outline".
2. **Outline review** — module cards with editable titles/summaries and their section rows: retitle,
   change kind, toggle required, drag to reorder, delete, add. Reuses the accept/edit card idiom from
   `ActionPlanReview.jsx`. → "Generate course".
3. **Progress** — a bar plus `stepLabel`, polling every 2 s, with Cancel. On `DONE`, navigates to
   `/clubpm/courses/:courseId`.

Closing the modal mid-generation does not cancel — the job keeps running, and `CoursesTab` shows a
"generating…" row for any of the member's non-terminal jobs so they can get back to it.

## API

```
POST   /api/outreach/courses/generate            { prompt, reference?, sourcePostIds? } → job (OUTLINING)
GET    /api/outreach/courses/generate/:jobId     → { status, progress, stepLabel, outline, courseId, error }
PATCH  /api/outreach/courses/generate/:jobId     { outline } — only while AWAITING_REVIEW
POST   /api/outreach/courses/generate/:jobId/run → starts stage 2 (AWAITING_REVIEW → GENERATING)
DELETE /api/outreach/courses/generate/:jobId     → cancel
GET    /api/outreach/courses/generate            → this member's recent jobs
```

Every route is scoped to `req.memberId` — a job is readable and cancellable only by its creator or an
admin. `PATCH` re-runs `validateCoursePlan` on whatever the client sends: the review screen is a
convenience, not a trust boundary, and a hand-crafted request must not be able to inject a
50-module plan.

## Verification

**Unit** (`backend/src/services/coursePlan.test.ts`, pure, `npx tsx`):
- `validateCoursePlan` drops unknown kinds, clamps to 8 modules / 10 sections / 50 total, and returns
  an empty plan for garbage rather than throwing
- a QUIZ section's `questionCount` clamps to a sane range and `passThreshold` to 0–100
- a module with no sections survives validation (the author may fill it) but is reported by
  `planSectionCount`
- `planSectionCount` matches the number of sections stage 2 will actually write

**Build gates:** `npm run build` at root; `npx prisma generate && npx tsc --noEmit` in `backend/`.

**Manual:**
1. Generate an outline from a three-paragraph prompt; confirm modules and mixed section kinds.
2. Edit the outline — rename a module, change a section from CONTENT to QUIZ, delete one, reorder —
   then generate, and confirm the course matches the **edited** outline exactly.
3. Watch `stepLabel` advance and `progress` reach 100.
4. Confirm the created course is `DRAFT`, has the right module/section tree, that CONTENT sections
   have real multi-section bodies, and that QUIZ questions have a correct answer and an explanation.
5. Confirm a QUIZ's questions test material from **its own module's** content.
6. Cancel mid-run; confirm it stops between sections and the partial course survives.
7. Restart the backend mid-run; confirm the job flips to `FAILED` with the restart message rather
   than spinning forever.
8. Close the modal mid-run and confirm `CoursesTab` still shows the job.
9. `PATCH` a hand-built 40-module outline with curl and confirm it is clamped to 8.
